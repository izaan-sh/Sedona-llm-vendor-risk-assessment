## 📌 Executive Summary

Sedona is a prototype platform that helps IT and security staff review vendor security questionnaires (**HECVAT**) against a university's approved security policies. It runs on a locally hosted LLM. In the reference Linux deployment, everything runs offline after installation, so no vendor or policy data leaves the machine.

The project goes beyond a simple chatbot. It combines retrieval, a structured evaluation method, and risk scoring to turn a 267-control questionnaire into a traceable, reviewable gap analysis. Key achievements include:

- Automating review of a **267-control, 25-section** HECVAT against internal security policies.
- Designing a **two-layer evaluation method** (vendor answer vs. HECVAT expectation, and policy alignment via RAG).
- Running a **RAG pipeline** on **ChromaDB** over the institution's policy knowledge base, with optional session-only supporting evidence such as a SOC 2 report.
- Deploying on a **university-provisioned Ubuntu GPU VM** with local models and **no external API calls** at runtime.
- Scoring risk using the university's **Risk Management Framework (RMF)**.
- Generating **PDF, PPTX and CSV** outputs from one set of findings, so they cannot disagree.
- Protecting access with **role-based accounts**, salted password hashes and CSRF protection.

---

## 🎯 The Problem

Reviewing a HECVAT is slow and inconsistent. Each answer has to be checked against internal policy before a risk rating can be assigned, results depend on the individual reviewer, and vendor answers are often vague or incomplete. Sending that material to a hosted LLM would also create a data handling risk of its own, which defeats the purpose of a risk tool.

## 📐 Architecture & Environment

The system runs inside a single university-provisioned VM boundary.

| Layer | Role / Specifications |
| :--- | :--- |
| **LLM Engine** | Linux (reference): `gemma-3-4b-it` served by a local **llama.cpp** server on the GPU. macOS: **Ollama** (Metal, or Ollama Cloud with a `-cloud` model tag) |
| **Embeddings** | `nomic-embed-text-v1.5`, always computed locally |
| **Retrieval** | **ChromaDB** vector store, in-process, over the policy knowledge base plus optional session-only evidence |
| **Scoring** | RMF scoring module (likelihood x impact) |
| **Backend** | FastAPI (Python) with authentication, sessions, uploads, follow-up Q&A and reports |
| **Frontend** | React + Vite web interface |
| **Reporting** | PDF, PPTX and CSV |
| **Deployment** | Ubuntu VM, T4-class GPU, 64 GB RAM, runs offline after installation |

**Flow:** the assessor uploads a HECVAT through the interface, which is parsed and matched against policy context in ChromaDB. The local LLM evaluates each control, the RMF scoring module rates the risk, and the reporting service generates the reports.

### 🔒 Why run the model locally?

Vendor security submissions and internal policies are sensitive. Running the model locally removes the exposure that a hosted API would create. This was a deliberate design decision, not a limitation we fell back on.

There is one caveat worth stating plainly. Privacy depends on which model you run. The reference Linux deployment keeps everything on the machine, but the macOS setup defaults to an Ollama Cloud model, which sends prompt content to an external service. Switching to a local model tag restores fully local behaviour. The first installation also needs internet access to download dependencies and model weights, so an air-gapped first install is not supported.

## 🧠 The Two-Layer Evaluation

Each HECVAT control is assessed in two layers, handled in a **single LLM inference pass** rather than two separate calls. This keeps the pipeline simpler and faster on a small local model.

| Layer | Question it answers | How |
| :--- | :--- | :--- |
| **Layer 1** | Does the vendor's answer meet what the HECVAT considers a compliant response? | Direct comparison against the expected HECVAT answer |
| **Layer 2** | Does the answer align with the university's own security policies? | Relevant policy text retrieved from ChromaDB and given to the model as context |

---

## 🚀 What Sedona Does

### Phase 1: Ingestion & Parsing
- An administrator adds the approved policy documents and the HECVAT template to the knowledge base.
- An assessor uploads a filled HECVAT (`.xlsx` or `.xlsm`), which is checked at upload so a bad workbook is caught straight away.
- Optional supporting evidence (PDF, such as a SOC 2 report) stays isolated to that session and never enters the institution-wide knowledge base.

### Phase 2: Evaluation
- Runs the two-layer evaluation on every applicable control.
- A control the model cannot judge reliably is flagged for manual resolution rather than guessed at.
- Asks the assessor follow-up questions, which can be answered or skipped.

### Phase 3: Risk Scoring
- Rates gaps using the RMF at five severities: **VERY HIGH, HIGH, MEDIUM, MINOR and LOW**.
- Results can be filtered by severity on the Results page.

### Phase 4: Reporting
- Produces PDF, PPTX and CSV outputs from one set of findings.
- The PDF and CSV carry every control in full. The PPTX is a fixed-length executive briefing.
- Each risk traces back to its source answer and policy.

## 🧩 Handling Coverage Gaps

Not every control can be assessed the same way. Sedona handles these cases explicitly instead of letting the model improvise:

| Situation | Example | How Sedona handles it |
| :--- | :--- | :--- |
| **Policy-covered control** | Most security controls | Full two-layer evaluation with policy context |
| **No matching policy** | ~18% of controls, mainly AI and IT accessibility sections | Retrieval returns nothing useful, so the control is flagged as a gap for human review |
| **Conditional section** | HIPAA, PCI DSS, on-premises | Gated by earlier vendor answers and treated as N/A when not applicable |
| **Vague vendor answer** | Unclear or incomplete response | Follow-up question generated for the assessor |

## ⚖️ Design Decisions

1. **Policy-grounded evaluation.** Relevant policy text is retrieved and given to the model alongside the vendor's answer, so it can judge alignment directly instead of guessing what the policy says.
2. **Small local model.** Gemma 3 4B is far less capable than large hosted models, but it fits the local-hosting requirement and the VM hardware.
3. **One backend per platform.** Linux uses llama.cpp on the GPU. macOS uses Ollama. The backend is chosen automatically by platform, and the application code is shared. There is no automatic CPU fallback on Linux: CPU is available only by deliberate choice and takes hours per assessment.
4. **Human in the loop.** Outputs are decision support for reviewers, not verdicts.
5. **Session-scoped evidence.** Supporting documents are isolated to their session so vendor material never contaminates the institutional knowledge base.

## 🔐 Access Control, Privacy & Reliability

**Access control**
- Every user signs in with their own account. There is no default account or password.
- Three roles: **Admin** (everything, plus user and knowledge base management), **Assessor** (upload, run assessments, generate reports), and **Viewer** (read-only, only for completed sessions assigned to them).
- Passwords are stored as salted hashes, the session cookie cannot be read by page scripts, requests that change data carry a CSRF token, and sessions expire after eight hours by default.
- Self-registered accounts always arrive as Viewers and must be promoted by an admin.

**Privacy**
- In the reference Linux deployment, no vendor or policy data leaves the host after installation.
- Embeddings are always computed locally on every platform.
- Cloud model tags on macOS send prompt content off the machine, so they should be avoided for real vendor data unless that is approved.

**Reliability**
- LLM hallucination is the main reliability concern, so every risk statement needs human review.
- Traceability lets reviewers check where each claim came from.

## ⚠️ Limitations

- HECVAT only covers so much. It cannot show a vendor's real security posture, so Sedona flags gaps rather than filling them in.
- A 4B model has limited reasoning depth compared to larger hosted models.
- Controls without matching internal policy cannot be meaningfully assessed through retrieval.
- Accuracy is a target, not a measured result. There was no reference dataset to measure against, so results have not been formally benchmarked.
- Findings differ between platforms, because they run different chat models.
- Output quality depends on the quality and completeness of the vendor's answers.

---

## 💡 What I Learned

- Evaluation design has to reflect what retrieval can and cannot actually cover. That matters more than prompt tweaking.
- Local deployment is a real trade-off: you gain data control and give up model capability. It is also only as private as the model you choose, since a cloud model tag sends data off the machine.
- Security assurance is mostly about gaps and ambiguity, not clean yes/no answers.
- In a team with a real client, figures and claims must be verified before they go into a deliverable, because unchecked numbers cause rework.
